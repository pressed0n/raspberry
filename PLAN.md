# Implementation Plan: Session authentication: Google sign-in + emailed one-time code

> Generated at: 2026-10-28 14:46:45

## Executive Summary
Two-factor login for the hosted path: Google OAuth proves identity, a 6-digit code sent to email proves inbox control, then an opaque session cookie admits the request. Built into the `resolveActor()` seam that already exists, so no route or MCP tool signature changes.

Design decisions, and why:

- **Opaque tokens, not JWTs.** 32 random bytes in the cookie, SHA-256 of that stored in `sessions`. No signing secret exists, so there is nothing to leak or rotate. DB read is required per request anyway to check revocation, so statelessness buys nothing.
- **No OAuth library.** `state` + PKCE (S256) generated with `node:crypto`. The callback exchanges the code server-to-server and fetches Google's `userinfo` over TLS with the resulting access token. Deliberate: it avoids hand-rolling id_token JWT signature verification, which is the single easiest thing to get catastrophically wrong in an auth implementation.
- **Code hashed with scrypt + per-row salt**, compared with `timingSafeEqual`. A DB leak does not yield live login codes. No global secret needed.
- **The 2nd factor is bound to the OAuth identity**, not a loose email string: the challenge row carries the verified `google_sub`, so a code cannot be replayed against a different account.
- **Allowlist by default.** This is a single-owner notes app. Without `RASPBERRY_ALLOWED_EMAILS`, the first verified account claims the instance and every other email is refused.

Three landmines this plan must defuse, all found in the current code:

1. **`requestAccessError()` returns `HOSTED_AUTH_PENDING` for *every* hosted request** (`access.ts:131`). Right now the transport gate is the only thing making hosted unreachable. It has to stop being an auth decision and become transport-only — and that edit must land in the *same commit* as real session verification, never before it, or the app is briefly open.
2. **`getService()` throws unless `RASPBERRY_LOCAL_DEV === "1"`** (`runtime.ts:6`). In hosted mode every route currently dies on that line. Auth resolution itself needs the database, so this gate has to be split: `getDatabase()` ungated (opening a file is not an auth decision), `getService()` gated on "local dev OR valid session config".
3. **Existing notes have no owner.** Pages live under `LOCAL_WORKSPACE_ID` with no membership row anyone can log in as. If you copy `data/raspberry.sqlite` to the laptop/VPS, your current notes become invisible behind your first real login. Needs an explicit claim step, not luck.

Also prerequisites, because auth tables cannot be added safely without them: **there is still no migration runner.** `schema_migrations` is written but never read, and `CREATE TABLE IF NOT EXISTS` silently no-ops on an existing database — so a new table would appear on fresh installs and mysteriously not appear on yours.

## Action Steps
1. P0 — Migration runner (prerequisite). Read `schema_migrations`, apply pending migrations in order, each in its own transaction, record version after commit. Migration 1 = current baseline DDL (idempotent, no-op on existing DBs), 2 = the existing ad-hoc child-link migration from `seed()`, 3 = auth schema. Tests: idempotent on second run, applies in order, records versions, rolls back a failed migration without leaving a version row.
2. P1 — Auth schema (migration 3) + session store. New tables: `accounts` (provider, subject, email — a table rather than `ALTER TABLE users ADD UNIQUE`, which SQLite cannot do), `sessions` (token_hash, user_id, created_at, expires_at absolute cap, last_seen_at, revoked_at, ip_hash, ua_hash), `login_challenges` (state_hash, PKCE, code_hash, code_salt, bound google_sub, attempts, expires_at, consumed_at), `auth_events` (hashed email/IP only, never codes). Session module: mint, verify, revoke, revoke-all-for-user, sliding touch throttled to once per 60s so a session lookup is not a write on every request. Tests: expired rejected, revoked rejected, unknown rejected, disabled user rejected, touch is not a write-per-request.
3. P2 — Google OAuth start + callback. `/api/auth/google/start` mints state + PKCE, binds both to a 10-minute HttpOnly `SameSite=Lax` cookie, redirects to Google. `/api/auth/google/callback` verifies state (constant-time), exchanges the code server-to-server, fetches userinfo over TLS, then requires `email_verified === true`, a present `sub`, and allowlist membership. Injectable `fetch` seam so CI never touches the network. Tests: state mismatch, missing/replayed cookie, `email_verified:false`, non-allowlisted email, `next` parameter that is an absolute URL (open-redirect guard).
4. P3 — Email one-time code. 6 digits from `crypto.randomInt` (never `Math.random`), scrypt-hashed with per-row salt, 10-minute TTL, single use, 5 attempts then the challenge is burned, 60s resend cooldown, max 5 sends. Mailer behind an interface with `console` (dev, clearly marked) and `smtp` backends. Tests: wrong code decrements, 5th wrong burns the challenge, expired rejected, reuse rejected, cooldown enforced, code from a challenge bound to account A fails against account B.
5. P4 — Wire the seam and retire the deny-all. `resolveActor()` does cookie → hash → joined `sessions ⋈ memberships` lookup → `Actor` with `clientId = session id` (which also kills the shared `"browser"` idempotency namespace). `requestAccessError()` becomes transport-only; `HOSTED_AUTH_PENDING` is removed in this same commit, nothing earlier. `runtime.ts` split into `getDatabase()` / `getService()`. `proxy.ts` keeps a cheap cookie-presence check only (docs are explicit: no DB in proxy) — browsers get a 302 to `/login?next=…`, API gets 401 JSON; real verification stays in `resolveActor`. `serve.mjs` stops refusing session mode and instead validates that every required variable is present, exiting with a named list if not. Tests: session mode with no cookie is 401 and never 200; local mode's existing 14 access cases still pass unchanged.
6. P5 — UI + operational surface. `/login` (Google button is a plain link, so CSP needs no `script-src` exception), `/login/code` with `autocomplete="one-time-code"`, POST `/api/auth/verify-code`, POST-only `/api/auth/logout` that deletes the session row rather than just clearing the cookie. `api-client` treats 401 as `unauthorized`, keeps the draft, and routes to re-login. Logout clears the `localStorage` drafts — on a shared machine those hold typed note content. Cookie is `__Host-raspberry_session` (Secure, Path=/, no Domain), falling back to an unprefixed name only for http hosted dev, with a boot-time log when it falls back.
7. P6 — Legacy workspace claim + docs. `RASPBERRY_OWNER_EMAIL` claims the existing `LOCAL_WORKSPACE_ID` and its pages on first login, so copying `data/raspberry.sqlite` to the VPS does not orphan your notes. Update `.env.example`, `SECURITY.md`, and `README` (which currently says the app is not ready to be exposed, and must stop saying that only when it is true). Add an `auth_events` review note to `SECURITY.md`. Push and confirm CI green on both build shapes.
8. P7 — Hardening pass after the flow works: tighter rate-limit buckets on `/api/auth/*`, per-email lockout counters in the DB (the in-memory limiter does not survive a process restart, and auth is exactly where that matters), audit rows for every rejected attempt, and a session sweeper for expired rows. Each sub-step verified by the suite, not by reading.

## Open Questions & Considerations
- 2nd factor channel: the OTP goes to the Google address by default, but if the inbox *is* the Gmail account then one Google compromise defeats both factors. Sending to a separate `RASPBERRY_OWNER_EMAIL` (non-Gmail) makes it genuinely two channels. My recommendation: separate address if you have one, otherwise accept that this is 'Google + Google'.
- Mail delivery: SMTP directly from a laptop on a residential IP will be rejected or spam-foldered by most providers — you realistically need a relay (Resend/SES/Postmark/Mailgun). Two backend options: nodemailer (one new pinned dependency, works with any SMTP relay) or a zero-dependency HTTPS `fetch` to one provider's API. My recommendation: nodemailer + SMTP, since it is provider-agnostic and lets you switch relays without a code change. Tell me which you prefer, or say 'console only for now' and I will ship the interface with the SMTP backend unwired.
- Break-glass: if the Google account is lost or Google locks it, you are locked out of your own notes. Options: a one-time recovery code shown exactly once at first login (stored hashed), or 'the local-only mode on the laptop still works'. I recommend both, with the recovery code printed in the terminal on first claim and never shown again.
- Scope check: multi-user stays out of this. Single-owner allowlist, one workspace. If you want real multi-tenant accounts (each Google user gets their own workspace) say so now — it changes the workspace-creation path and the claim step, and it is much cheaper to build in now than to retrofit.
